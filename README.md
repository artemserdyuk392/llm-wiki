# LLM-wiki

Пилот личных баз знаний на основе концепции **LLM-wiki**: вместо поискового
индекса по кускам документов LLM ведёт **производную вики** — набор связанных
Markdown-страниц, которые она сама пишет и дополняет по мере поступления новых
источников.

> Статус: **пилот**. Инструмент работает и используется, но собирается обратная
> связь по качеству получаемых баз знаний. Приглашаем попробовать на своих
> материалах — см. раздел [Участие в пилоте](#участие-в-пилоте).

## Идея в двух абзацах

Классический RAG режет документы на чанки, кладёт их в индекс и на каждый вопрос
достаёт похожие куски. Документы при этом остаются грудой разрозненных фрагментов:
система не знает, что «процесс X» из одного отчёта и «процесс X» из регламента —
одно и то же.

LLM-wiki работает иначе. Источники складываются в иммутабельный каталог `raw/`,
а модель постепенно строит из них **вики**: страница на документ, страница на
сущность (процесс, система, роль, риск), страница на концепт. При добавлении
нового источника агент читает его целиком, находит уже существующие страницы по
теме и **дополняет** их, а не создаёт дубликаты. Идентичность страницы — это имя
файла, поэтому «Retriever» из десяти разных документов собирается в одну страницу
с десятью ссылками на источники. Онтологию задаёт человек в файле `SCHEMA.md`,
и переписать её модель не может.

На выходе получается база знаний, которую можно читать глазами, вести в git,
править руками и отдавать людям — в отличие от векторного индекса.

## Чем это не является

- Это **не замена поисковому движку**. Ответ на вопрос собирается чтением страниц
  вики, а не поиском по эмбеддингам. На сотнях страниц это работает, на десятках
  тысяч — нет.
- Это **не автоматический аналитик**. Модель пересказывает и связывает содержимое
  источников; она не проверяет факты и не выносит суждений.
- Это **не хранилище документов**. `raw/` — рабочая папка входа, а не архив.

## Требования

- Python 3.9+ (проверено на 3.12)
- `requests` — единственная обязательная внешняя зависимость
- Доступ к внутреннему LLM-шлюзу (переменные `GIGACHAT_API_URL` и `JPY_API_TOKEN`)

Конвертация офисных форматов опирается на дополнительные библиотеки, но
**без них инструмент тоже работает** — просто с меньшим списком поддерживаемых
форматов. Подробности — в разделе [Какие файлы можно загружать](#какие-файлы-можно-загружать).

## Установка

**Вариант 1 — архив** (если файловый перенос доступен):

```bash
unzip llm-wiki-3.0.1.zip -d /путь/к/проекту
cd /путь/к/проекту/llm-wiki
python3 wiki.py --version
```

**Вариант 2 — ASCII-инсталлятор** (если между вами и сервером только буфер обмена):

```bash
python3 install_llm_wiki.py /путь/к/проекту
```

`install_llm_wiki.py` целиком состоит из 7-битного ASCII, поэтому переживает любую
пересылку через терминал, редактор или буфер обмена без перекодировки. Внутри
лежит тот же архив плюс контрольная сумма: при повреждённой вставке инсталлятор
откажется разворачивать пакет.

> **Не копируйте `.py`-файлы текстом через Windows-редакторы.** Они сохраняют в
> ANSI (cp1251), после чего Python отказывается читать исходники: `SyntaxError:
> (unicode error) 'utf-8' codec can't decode byte 0xcb`. Лечится `iconv`, но проще
> не создавать проблему — см. [Частые грабли](#частые-грабли).

### Переменные окружения

```bash
export GIGACHAT_API_URL="http://<адрес-шлюза>/v1/gc"
export JPY_API_TOKEN="<токен>"
```

Проверить, что всё на месте:

```bash
python3 wiki.py doctor
```

![Проверка окружения командой doctor](docs/img/doctor.png)

`doctor` показывает версию Python, наличие каталогов проекта, заданность
переменных окружения, список доступных конвертеров и делает тестовый запрос к
модели. Начинать стоит с него.

## Первые шаги

### 1. Создать структуру проекта

```bash
mkdir ~/my-wiki && cd ~/my-wiki
python3 /путь/к/llm-wiki/wiki.py init
```

Появятся каталоги `raw/`, `raw_md/`, `wiki/` и заготовка `SCHEMA.md`.

### 2. Положить документы

Скопируйте материалы в `raw/`. Вложенные папки поддерживаются — структура
переносится в `raw_md/` как есть.

```bash
cp ~/Документы/регламенты/*.docx raw/
```

### 3. Запустить интерфейс

```bash
python3 /путь/к/llm-wiki/wiki.py
```

![Главное меню](docs/img/menu.png)

Управление — стрелками ↑/↓ и Enter либо цифрой пункта. `q` — назад, в главном
меню — выход. Если терминал не поддерживает управление клавишами (запуск через
пайп, экзотическая консоль), меню автоматически переключается на ввод номера
строкой.

### 4. Загрузить источники в вики

Пункт **INGEST** → «Все новые файлы из raw/».

![Процесс загрузки источников](docs/img/ingest.png)

Каждый файл проходит два этапа: сначала детерминированная конвертация в Markdown
(строка `конвертация: raw_md/...`), затем агент читает результат и раскладывает
содержимое по страницам вики (строки вида `[ 7] write_file(...) -> ok`).

Первый прогон удобно ограничить: на вопрос про лимит файлов ответьте `3` — так вы
увидите, что получается, не потратив час.

### 5. Спросить у базы знаний

Пункт **QUERY**.

![Ответ на вопрос к базе знаний](docs/img/query.png)

Агент сначала читает `wiki/index.md`, затем открывает релевантные страницы и
отвечает по их содержимому, указывая использованные файлы.

### 6. Посмотреть, что получилось

Результат лежит в `wiki/` обычными Markdown-файлами — их можно открыть любым
редактором.

![Пример страницы вики](docs/img/wiki-page.png)

Для сводной картины есть пункт **REPORT**: он собирает HTML-отчёт с метриками
объёма, связности, битых ссылок и страниц-сирот.

![HTML-отчёт по базе знаний](docs/img/report.png)

## Что появляется в проекте

```
my-wiki/
├── SCHEMA.md               # онтология и правила ведения вики (пишет человек)
├── raw/                    # исходные документы в любых форматах. ИММУТАБЕЛЬНЫ
├── raw_md/                 # Markdown-копии raw/ с YAML-frontmatter (генерируется)
├── wiki/                   # база знаний — единственное место записи агента
│   ├── index.md            # карта вики: таблица на каждый тип страниц
│   ├── log.md              # append-only журнал изменений
│   ├── sources/            # страница на документ
│   ├── entities/           # процессы, системы, подразделения, роли, риски
│   └── concepts/           # термины и методы
├── backups/                # автоматические копии wiki/ (последние 20)
├── .llm_wiki_state.json    # журнал: что сконвертировано и что загружено
└── wiki_report.html        # HTML-отчёт (создаётся по запросу)
```

Разделение на три слоя не декоративное, оно защищает от потери данных:
`raw/` агенту недоступен на запись программно, `raw_md/` тоже, писать он может
только в `wiki/` и только файлы `.md`. Перед каждым прогоном и каждые три файла
делается бэкап `wiki/`.

## Функциональные возможности

Всё доступно и через меню, и командой — для скриптов и cron.

| Операция | Команда | Что делает |
| --- | --- | --- |
| **INGEST** | `wiki.py ingest --all` | Конвертирует источники и загружает их в вики. Уже обработанные пропускает |
| **QUERY** | `wiki.py query "вопрос"` | Отвечает на вопрос по содержимому вики со ссылками на страницы |
| **CONVERT** | `wiki.py convert --all` | Только конвертация `raw/` → `raw_md/`, без обращений к модели |
| **STATUS** | `wiki.py status` | Что обработано, что в очереди, какие форматы, сколько страниц и бэкапов |
| **REPORT** | `wiki.py report -o отчёт.html` | HTML-отчёт: объём, связность, битые ссылки, сироты, топ страниц |
| **LINT** | `wiki.py lint` | Проверка целостности вики силами модели: битые ссылки, дубликаты, противоречия |
| **REINDEX** | `wiki.py reindex` | Пересборка `index.md` в единую карту без дублей |
| **BACKUP** | `wiki.py backup` | Копия `wiki/` вручную |
| **DOCTOR** | `wiki.py doctor` | Диагностика окружения, конвертеров и связи с моделью |
| **INIT** | `wiki.py init` | Создание структуры проекта |

Полезные флаги `ingest`:

| Флаг | Назначение |
| --- | --- |
| `--all` | Все необработанные файлы из `raw/` |
| `--limit N` | Не больше N файлов за прогон |
| `--force` | Обработать заново, игнорируя журнал |
| `--convert-only` | Только конвертация, без вызовов модели |
| `--stop-on-error` | Прервать прогон на первой ошибке |
| `--no-backup` | Отключить автоматические бэкапы |

Прогон можно прерывать по Ctrl+C: журнал сохраняется, следующий запуск продолжит
с того же места.

## Настройки

Меняются тремя способами, по возрастанию приоритета: переменные окружения → флаги
командной строки → пункт **SETTINGS** в меню (действует до конца сеанса).

### Что реально стоит настраивать

**Модель** (`GIGACHAT_MODEL`, `--model`). По умолчанию `glm-5.2`.

| Модель | Особенности |
| --- | --- |
| `glm-5.2` | Потолка генерации нет, но длинную страницу может писать до 300 секунд |
| `GigaChat-3-Ultra` | Стабильна, не тратит reasoning-токены, ~40 секунд на страницу |
| `Qwen3.5-397b` | Обязателен явный `max_tokens`, иначе обрыв на 2048 токенах |

**Режим инструментов** (`GIGACHAT_TOOL_MODE`, `--tool-mode`). По умолчанию
`prompt` — модель возвращает JSON-действие текстом ответа. На внутреннем шлюзе он
работает заметно стабильнее нативного function calling. `native` оставлен для
шлюзов, где function calling поддержан полноценно.

**Лимит генерации** (`GIGACHAT_MAX_TOKENS`, по умолчанию 8000). Если в логе часто
мелькает `[truncated 1/3] ответ оборван по лимиту` — поднимайте до 16000. Обрыв не
опасен: недописанный вызов отбрасывается, а модель получает указание писать
страницу частями. Но каждый такой обрыв — потраченный впустую запрос.

**Бэкенд конвертации** (`LLM_WIKI_CONVERT_BACKEND`, `--convert-backend`). По
умолчанию `auto` с автоматическим фолбэком. Явный выбор (`cardify`, `markitdown`,
`builtin`) нужен, когда хочется сравнить качество извлечения текста.

### Остальные переменные

| Переменная | По умолчанию | Назначение |
| --- | --- | --- |
| `GIGACHAT_API_URL` | — | Адрес шлюза (обязательна) |
| `JPY_API_TOKEN` | — | Токен доступа (обязательна) |
| `GIGACHAT_MAX_STEPS` | 120 | Потолок шагов агента на одну операцию |
| `GIGACHAT_TIMEOUT` | 900 | Таймаут одного HTTP-запроса, секунд |
| `GIGACHAT_MAX_ATTEMPTS` | 6 | Попыток на запрос при сетевых сбоях и 5xx |
| `GIGACHAT_SLEEP` | 1.0 | Минимальный интервал между запросами, секунд |
| `GIGACHAT_VERIFY_SSL` | true | Проверка сертификата шлюза |
| `LLM_WIKI_HEARTBEAT` | 15 | Период сообщений «жду ответ модели», секунд; 0 — выключить |
| `LLM_WIKI_BACKUP_EVERY` | 3 | Бэкап `wiki/` каждые N обработанных файлов |
| `LLM_WIKI_BACKUP_KEEP` | 20 | Сколько последних бэкапов хранить |
| `LLM_WIKI_IMAGE_MODE` | folder | Что делать с картинками: `folder`, `base64`, `skip` |
| `LLM_WIKI_MAX_TABLE_ROWS` | 500 | Потолок строк на таблицу или лист Excel |
| `LLM_WIKI_MAX_READ_CHARS` | 100000 | Потолок символов за одно чтение файла агентом |
| `LLM_WIKI_ROOT` | `.` | Корень проекта по умолчанию |
| `LLM_WIKI_TITLE` | LLM WIKI | Надпись в баннере |
| `LLM_WIKI_VERBOSE` | 0 | Подробные логи, включая логи конвертеров |

## Какие файлы можно загружать

В `raw/` можно класть файлы разных форматов вперемешку — перед загрузкой в вики
каждый автоматически конвертируется в Markdown.

| Формат | Что извлекается | Чем |
| --- | --- | --- |
| `.docx` | Текст с уровнями заголовков, таблицы, метаданные, картинки | cardify / python-docx |
| `.pdf` | Постраничный текст | cardify / pdfplumber / pypdf |
| `.pptx` | Слайды, таблицы, заметки докладчика, текст из сгруппированных фигур | cardify / python-pptx |
| `.xlsx`, `.xlsm` | Листы как Markdown-таблицы | cardify / openpyxl |
| `.ipynb` | Markdown-ячейки, код, текстовые выводы | встроенный |
| `.csv`, `.tsv` | Таблица с автоопределением разделителя и кодировки | встроенный |
| `.html`, `.htm` | Текст с заголовками и списками, без скриптов и стилей | встроенный |
| `.eml` | Заголовки письма и тело; вложения отмечаются, но не извлекаются | встроенный |
| `.md`, `.txt`, `.log` | Как есть, добавляется frontmatter | встроенный |
| `.json`, `.yaml`, `.xml`, `.py`, `.sql`, `.sh` | В виде блока кода | встроенный |

Порядок бэкендов при `auto`: **cardify** (штатный движок СВА, если установлен) →
**markitdown** → **встроенные конвертеры** → **stdlib**. Если выбранный бэкенд
упал, следующий подхватывает автоматически, прогон не прерывается.

Форматы из последних шести строк таблицы работают на голой стандартной библиотеке
и доступны всегда. Для `.docx`, `.pdf`, `.pptx` нужны `python-docx`, `pdfplumber`
(или `pypdf`), `python-pptx` — что именно доступно в вашем окружении, покажет
`doctor`.

### Ограничения, о которых стоит знать заранее

- **Сканы PDF без текстового слоя** не распознаются: OCR в пилоте нет. Такой файл
  сконвертируется в почти пустой Markdown, а в предупреждениях появится отметка.
- **Очень большие файлы** (сотни тысяч символов) агент читает кусками и может
  упереться в лимит шагов, собрав страницу только по началу документа. Для таких
  материалов лучше заранее разрезать исходник на логические части.
- **Изображения и схемы** сохраняются как файлы, но их содержимое не
  распознаётся — на слайде со схемой в вики попадёт только текст подписей.
- **Вложения писем** не извлекаются; если они важны, положите их в `raw/` отдельно.

Каждая Markdown-копия в `raw_md/` содержит YAML-frontmatter с провенансом: путь и
контрольная сумма источника, формат, использованный конвертер, предупреждения.
Посмотреть, что реально увидит модель, можно до траты токенов — операцией
`convert`, а затем просто открыв файл в `raw_md/`.

## SCHEMA.md — главная ручка

`SCHEMA.md` — это контракт, который агент обязан соблюдать: какие бывают типы
страниц, в каких каталогах они лежат, когда создавать новую страницу, а когда
дополнять существующую. Модель не может его переписать.

Заготовка, которую создаёт `init`, рассчитана на аудиторский домен: источники,
сущности, концепты. **Под свой материал её нужно править** — это и есть основная
содержательная работа при запуске своей базы знаний. От схемы зависит, во что
превратится корпус: те же документы при разной схеме дадут разные вики.

Что стоит описать в своей схеме:

1. Типы страниц вашего домена и каталог для каждого.
2. Критерий создания новой страницы (например: тема встречается в двух и более
   источниках).
3. Что делать с противоречиями между источниками — сглаживать нельзя, фиксируйте
   оба утверждения со ссылками.
4. Обязательные разделы страницы, если они важны для дальнейшего использования.

После правки схемы имеет смысл прогнать `ingest --force` на небольшой выборке и
посмотреть, что изменилось.

## Частые грабли

**`SyntaxError: 'utf-8' codec can't decode byte 0xcb`** — файлы скрипта перенесли
текстом через Windows-редактор, и они сохранились в cp1251. Лечение:

```bash
for f in wiki.py llm_wiki/*.py; do
    iconv -f CP1251 -t UTF-8 "$f" -o "$f.tmp" && mv "$f.tmp" "$f"
done
```

Профилактика — переносить архивом или инсталлятором `install_llm_wiki.py`.

**Кажется, что процесс завис.** Скорее всего он просто ждёт модель: на длинную
страницу уходят минуты. Раз в 15 секунд в вывод идёт строка
`... шаг 7/120: жду ответ модели 45 c`. Если такие строки идут — всё в порядке.
Если не идут вовсе, значит процесс действительно встал; это баг, сообщите.

**`[bad json 1/3]`** — модель вернула сломанный JSON-ответ. Скрипт сам просит
переделать, до трёх раз. Единичные появления нормальны.

**Агент создаёт дубликаты страниц** («retriever-as» и «as-retriever»). Признак
того, что схема недостаточно строга либо `index.md` разросся и модель перестала
находить существующие страницы. Помогает `reindex`, а в тяжёлых случаях — правка
`SCHEMA.md`.

**Прогон прервался на середине.** Ничего не потеряно: обработанные файлы отмечены
в журнале, `wiki/` забэкаплена. Просто запустите ту же команду снова.
