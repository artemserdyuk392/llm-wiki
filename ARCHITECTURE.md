## Общая картина

Система состоит из двух контуров с принципиально разной природой.

**Контур 1 — детерминированный.** Конвертация документов в Markdown. Никаких
обращений к модели, полностью воспроизводимо, результат кэшируется по контрольной
сумме источника. Если конвертация даёт плохой текст — виноват конвертер, и это
чинится без LLM.

**Контур 2 — агентный.** Модель в цикле «подумать → вызвать инструмент →
получить результат» читает Markdown и пишет страницы вики. Недетерминирован,
стоит токенов, требует защиты от собственных ошибок модели.

Разделение сделано намеренно: любой сбой можно локализовать. Плохо извлёкся
текст из PDF — смотрим `raw_md/`, не трогая модель. Текст извлёкся хорошо, а
страница получилась бессвязной — вопрос к схеме и промпту.

```
   raw/                     raw_md/                      wiki/
┌───────────┐          ┌──────────────┐            ┌──────────────┐
│ .docx     │          │ .docx.md     │            │ index.md     │
│ .pdf      │ ──────►  │ .pdf.md      │ ──────►    │ log.md       │
│ .pptx     │ конвер-  │ .pptx.md     │  агент     │ sources/     │
│ .xlsx     │  тация   │ + frontmatter│  + LLM     │ entities/    │
│ .md       │          │ + .assets/   │            │ concepts/    │
└───────────┘          └──────────────┘            └──────────────┘
 иммутабелен            генерируется,               единственное
 для всех               иммутабелен для агента      место записи

        │                      │                          │
        └──────────┬───────────┘                          │
                   ▼                                      ▼
        .llm_wiki_state.json                       backups/wiki-<дата>
        (sha256 источников:                        (перед стартом и
         что сконвертировано,                       каждые N файлов)
         что загружено в вики)
```

Ключевое архитектурное решение: **источник истины неизменяем**. `raw/` защищён
программно, `raw_md/` тоже. Всё, что модель способна испортить, лежит в `wiki/`
и покрыто бэкапами.

## Структура пакета

```
wiki.py                  # лаунчер; чистый ASCII, ловит битую кодировку пакета
llm_wiki/
├── config.py            # объект Settings (S) + неизменяемые константы
├── ui.py                # цвета, ASCII-шрифт, баннер, меню, ввод
├── convert.py           # контур 1: бэкенды конвертации, frontmatter, кэш
├── agent.py             # контур 2: инструменты, промпты, транспорт, циклы
├── state.py             # журнал обработки, отпечатки файлов, бэкапы
├── ops.py               # операции: init, convert, ingest, status, doctor
├── report.py            # метрики базы знаний и генерация HTML
└── cli.py               # интерактивное меню и разбор аргументов
```

Зависимости направлены в одну сторону, циклов нет:

```
cli ──► ops ──► agent ──► convert ──► state ──► config
 │       │        │          │          │         ▲
 └───────┴────────┴──────────┴──────────┴─────────┘
                        все ──► ui, config
```

### Про `Settings`

Все изменяемые параметры живут в единственном мутабельном объекте `config.S`.
Модули импортируют **объект**, а не значения из него:

```python
from .config import S
...
payload = {"model": S.model, "max_tokens": S.max_tokens}
```

Так флаг `--model` и меню SETTINGS меняют поведение во всех модулях сразу. Если
добавляете новый параметр — заводите поле в `Settings.__init__`, иначе меню его
не увидит, а импорт по значению разойдётся между модулями.

Неизменяемые вещи (`RAW_DIR_NAME`, `RETRY_STATUSES`, `TEXT_EXTENSIONS`) остаются
константами модуля.

## Слой 1: конвертация

Точка входа — `convert.ensure_markdown(root, rel_source, state, force)`.

### Выбор бэкенда

`choose_backend(extension)` возвращает предпочтительный бэкенд, а
`convert_source` строит из него цепочку с фолбэком:

```python
order = [choose_backend(extension)]
order += [b for b in ("cardify", "builtin", "markitdown") if b not in order]
```

Каждый бэкенд пробуется по очереди; исключение или пустой результат означают
переход к следующему, а накопленные ошибки попадают в поле `fallbacks` отчёта.
Прогон из-за одного проблемного файла не прерывается.

| Бэкенд | Что это | Когда выбирается |
| --- | --- | --- |
| `cardify` | Внутренняя библиотека СВА | Установлена и знает расширение |
| `markitdown` | Microsoft MarkItDown | Установлен, расширение не покрыто остальными |
| `builtin` | Конвертеры этого пакета | Всегда, когда расширение есть в `BUILTIN_CONVERTERS` |

Интеграция с cardify намеренно сделана через **опциональный импорт**, а не
копированием кода: пакет тянет pydantic, structlog, click и markitdown, которых
во внутреннем контуре может не быть. Проверка доступности кэшируется
(`_cardify_cache`), логирование cardify приглушается через `_hush_cardify()` —
иначе он засыпает stdout INFO-строками.

### Доработка cardify для PPTX

cardify не обрабатывает сгруппированные фигуры PowerPoint и сообщает о них
как о `skipped complex_shape`. На слайдах со схемами это означает потерю
практически всего содержания. После конвертации мы ловим такие предупреждения и
дочитываем текст групп самостоятельно:

```python
if source.suffix.lower() == ".pptx" and any("complex_shape" in w for w in warnings):
    recovered = _pptx_group_texts(source, markdown)
```

`_iter_pptx_shapes` рекурсивно раскрывает группы; восстановленный текст, которого
нет в основном выводе, дописывается отдельной секцией.

### Формат результата

`raw/отчёты/q1.docx` → `raw_md/отчёты/q1.docx.md` (картинки — в
`raw_md/отчёты/q1.docx.assets/`). Расширение исходника сохраняется в имени, чтобы
`report.pdf` и `report.docx` не схлопнулись в один файл.

Каждый результат получает YAML-frontmatter:

```yaml
---
source: raw/docs/reglament.docx      # оригинальный путь — на него ссылается вики
source_sha256: a4af77772a1d3c6d      # первые 16 символов отпечатка
source_bytes: 36973
format: docx
converted_at: "2026-09-28T14:35:53"
converted_by: "cardify:DocxConverter"
generator: llm_wiki 3.0.1
author: Иванов И.И.                  # метаданные документа, если есть
conversion_warnings:
  - "skipped embedded_ole_object: ..."
---
```

`yaml_frontmatter()` — минимальный сериализатор на регулярках: строки, числа,
списки. PyYAML сознательно не используется, чтобы не тащить зависимость ради
двадцати строк.

### Кэш

`ensure_markdown` сверяет sha256 источника с записью в `state["converted"]`.
Совпало и файл на месте — конвертация пропускается. Изменился исходник —
переконвертируется автоматически. `--force` игнорирует кэш.

## Слой 2: агент

### Системный промпт

Собирается в `agent.build_system_prompt(schema, tool_mode)` из трёх частей:

1. **Правила поведения** — один вызов инструмента за ответ, не выдумывать
   содержимое файлов, не считать файл изменённым до `ok=true`.
2. **Карта каталогов** — что где лежит, что иммутабельно, что ссылки в вики
   должны указывать на оригинальный путь из `source`, а не на Markdown-копию.
3. **`SCHEMA.md` целиком** — онтология проекта, заданная человеком.

В режиме `prompt` добавляется четвёртая часть — описание JSON-протокола.

`SCHEMA.md` ищется по цепочке `SCHEMA.md` → `CLAUDE.md` → `AGENTS.md`; если
ничего нет, операция падает с указанием запустить `init`.

### Промпты операций

`operation_prompt(operation, value, md_path)` формирует задание. Для `ingest`
передаются **оба** пути: оригинальный (для ссылок) и Markdown-копия (для чтения).

### Два протокола

**`prompt` (по умолчанию).** Модель возвращает ровно один JSON-объект текстом:

```json
{"tool":"read_file","arguments":{"path":"wiki/index.md","start_line":1,"max_lines":400}}
{"tool":"write_file","arguments":{"path":"wiki/concepts/rag.md","content":"...","mode":"overwrite"}}
{"final":"Изменены: wiki/concepts/rag.md, wiki/index.md"}
```

Разбор — `extract_json_object()`: снимает markdown-заборы, при неудаче вырезает
текст между первой `{` и последней `}`, при повторной неудаче парсит с
`strict=False` (частый брак моделей — сырые переводы строк внутри строкового
литерала). Результат инструмента возвращается следующим сообщением как
`TOOL_RESULT {...}`.

**`native`.** Штатный function calling: схемы функций уходят в поле `functions`,
ответ модели содержит `function_call`, результат возвращается сообщением с ролью
`function`. Исходное сообщение ассистента кладётся в историю целиком, вместе с
`functions_state_id` — иначе шлюз теряет контекст вызова.

Оба цикла ограничены `S.max_steps` (120) шагами.

## Инструменты модели

Три инструмента, все — в классе `agent.WikiTools`.

| Инструмент | Аргументы | Ограничения |
| --- | --- | --- |
| `list_files` | `path` | Только внутри корня проекта |
| `read_file` | `path`, `start_line`, `max_lines` | Только текстовые расширения, максимум 1000 строк и 100 000 символов за вызов |
| `write_file` | `path`, `content`, `mode` | Только `wiki/**.md`, только `overwrite` или `append` |

### Защитные проверки

`_safe_path()` резолвит путь и сверяет общий префикс с корнем проекта — выход за
пределы через `../` невозможен.

`write_file` последовательно отклоняет запись в `raw/`, в `raw_md/`, за пределы
`wiki/` и файлы не с расширением `.md`. Отдельно стоит **защита от обнуления**:

```python
if mode == "overwrite" and target.is_file():
    if old_size > 200 and new_size < old_size // 4:
        raise ValueError("Перезапись отклонена: ...")
```

Это ответ на реальную поломку: модель, получив задание «добавь строку в
index.md», иногда возвращала overwrite с одной новой строкой вместо полного
файла, стирая карту вики. Теперь такая запись отклоняется, а модель получает
объяснение и делает по-другому.

Запись `overwrite` **атомарна**: сначала временный файл рядом, затем
`os.replace()`. Оборванный процесс не оставит наполовину записанную страницу.

### Обработка ошибок инструментов

`WikiTools.execute()` ловит любое исключение и возвращает его модели как данные:

```python
{"ok": false, "error": "PermissionError", "message": "Каталог raw/ иммутабелен..."}
```

Ошибка инструмента — это сообщение агенту, а не аварийное завершение. Модель
читает объяснение и выбирает другое действие.

## Работа с API

Единственная точка обращения к модели — `agent.post_chat(payload, label)`.

```
POST {GIGACHAT_API_URL}/chat/completions
Authorization: Bearer {JPY_API_TOKEN}
Content-Type: application/json

{
  "model": "glm-5.2",
  "messages": [...],
  "temperature": 0.01,
  "max_tokens": 8000,
  "n": 1,
  "functions": [...],        // только в режиме native
  "function_call": "auto"    // только в режиме native
}
```

`temperature: 0.01` — задача требует воспроизводимости, а не разнообразия.

Ответ считается пригодным, только если пришёл HTTP 200, тело разобралось как
JSON и в нём есть непустой `choices`. Всё остальное — повод для повтора.

## Надёжность

Четыре механизма, каждый появился из конкретной поломки на реальном прогоне.

**Ретраи.** Коды `408, 409, 425, 429, 5xx`, сетевые ошибки, не-JSON и пустой
`choices` → повтор с экспоненциальной паузой и джиттером (`_retry_delay`),
до `S.max_attempts` раз. Прочие 4xx повторять бессмысленно — сразу `ApiError`.

**Троттлинг.** `_throttle()` выдерживает минимальный интервал между запросами
(`GIGACHAT_SLEEP`), чтобы не упираться в лимиты шлюза.

**Обрыв по лимиту токенов.** `finish_reason == "length"` означает, что ответ
оборван на полуслове — и если это был `write_file`, в аргументах лежит обрубок
страницы. Такой ответ **не применяется**: он отбрасывается, модель получает
`TRUNCATED_NUDGE` с требованием писать частями (`overwrite` + `append`), счётчик
подряд идущих обрывов доходит до трёх — дальше осмысленная ошибка с советом
поднять `max_tokens`.

**Пустой ответ.** HTTP 200 с пустым `content` — повтор, со второй попытки с
подсказкой `CONTINUE_NUDGE`.

**Heartbeat.** `Heartbeat` — контекстный менеджер с демон-потоком, который раз в
`S.heartbeat` секунд пишет в stderr, сколько уже длится ожидание:

```
... шаг 7/120: жду ответ модели 45 c
```

Появился потому, что долгая генерация (у glm-5.2 до 300 секунд на страницу) была
визуально неотличима от зависшего процесса.

## Состояние и бэкапы

`.llm_wiki_state.json` в корне проекта:

```json
{
  "version": 2,
  "converted": {
    "raw/docs/reglament.docx": {
      "sha256": "a4af...", "markdown": "raw_md/docs/reglament.docx.md",
      "backend": "cardify:DocxConverter", "warnings": [],
      "converted_at": "2026-09-28T14:35:53"
    }
  },
  "ingested": {
    "raw/docs/reglament.docx": {
      "sha256": "a4af...", "size": 36973, "ingested_at": "2026-09-28T14:36:10"
    }
  }
}
```

Два независимых журнала: файл может быть сконвертирован, но ещё не загружен в
вики (например, после `--convert-only`). Ключ — относительный путь, значение
привязано к sha256: правка источника автоматически ставит его обратно в очередь.

Запись состояния атомарна (временный файл + `os.replace`) и выполняется **после
каждого файла**, а не в конце прогона — прерывание по Ctrl+C не теряет работу.

**Бэкапы.** `shutil.copytree` каталога `wiki/` в `backups/wiki-<timestamp>-<tag>`:
перед стартом ingest, каждые `backup_every` файлов, в конце, а также перед `lint`
и `reindex`. Хранятся последние `backup_keep` штук, старые удаляются
(`prune_backups`). Восстановление — обычное копирование каталога назад.

## Отчёт

`report.analyze_wiki()` обходит `wiki/**.md` и считает:

- объём: файлы, символы, слова, строки, блоки кода, строки таблиц;
- ссылки: wiki-ссылки `[[...]]` и markdown-ссылки, с разделением на внутренние и
  внешние;
- битые ссылки — цель не резолвится ни по прямому пути, ни по имени файла;
- сироты — страницы без входящих ссылок (`index.md` исключён);
- граф связей: исходящие и входящие ссылки по страницам.

Сырой слой считается отдельно: количество файлов и объём — по `raw/`, а символы и
слова — по `raw_md/`. Это важная деталь: считать символы по `raw/` бессмысленно,
потому что `.pdf` и `.pptx` — бинарники. Отношение символов `raw_md/` к символам
`wiki/` даёт «степень сжатия» — насколько вики компактнее исходников.

HTML самодостаточен: стили инлайном, ни одного внешнего ресурса — открывается
в изолированном контуре.

## Как расширять

### Добавить формат

1. Написать функцию с сигнатурой `(source: Path, assets_dir: Path) -> (markdown, meta, warnings)`.
2. Зарегистрировать её в `BUILTIN_CONVERTERS` по расширению.

Конвертер обязан быть офлайновым и не бросать на пустом входе — вернуть пустую
строку достаточно, цепочка фолбэка разберётся.

### Добавить операцию

1. Функция `do_<operation>(root, ...)` в `ops.py`.
2. Имя в список `OPERATIONS` и ветка в `main()` в `cli.py`.
3. Пункт в список меню в `interactive()`.

Если операция обращается к модели — берите промпт из `operation_prompt()` и
вызывайте `run_agent()`, не пишите обращение к API напрямую.

### Добавить настройку

Поле в `Settings.__init__` с чтением `os.getenv`, при необходимости — флаг в
`parse_cli()` и пункт в `menu_settings()`.

## Известные ограничения

**Индекс не масштабируется.** При добавлении источника модель просматривает
`wiki/index.md` целиком. На паре сотен страниц он перестаёт помещаться в разумный
контекст, и агент начинает промахиваться мимо существующих страниц, создавая
дубликаты. Решение — шардирование индекса по типам сущностей и двухфазный ingest
(сначала выбор раздела, потом работа внутри него). В пилоте не реализовано.

**Большие источники.** Файл на 300+ тысяч символов агент читает кусками по 400
строк и может исчерпать лимит шагов, собрав страницу по началу документа.
Напрашивается нарезка по заголовкам на этапе конвертации с порогом по символам.

**Нет OCR.** Сканы PDF и текст на картинках не распознаются.

**Нет параллелизма.** Источники обрабатываются строго последовательно. Это
сознательный выбор: параллельные агенты писали бы в одни и те же страницы вики и
затирали правки друг друга. Безопасный параллелизм требует блокировок на уровне
страниц.

**Нет проверки фактов.** Агент пересказывает источники. Противоречия он по
инструкции фиксирует как противоречия, но истинность утверждений не оценивает.
